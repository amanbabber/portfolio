Case study 01 · Platform rebuild

Rebuilding the contract dashboard under a live 2M-contract/year load

The entry point to the platform for every mobile buyer was taking up to 20 seconds to load, and blocking every other action until it did. This is the diagnosis, the rebuild, and the tradeoff I'd revisit next.

My role
PM — scope, spec, sprint mgmt, QA
Team
3 senior engineers + me
Timeline
~2.5 months
Load time
15–20s → 3–4.5s
Context

The busiest page on the platform was also the oldest

ScopeWorker runs the contract lifecycle for enterprise telecom infrastructure clients. For a single client alone, one program creates over 2.3 million contracts a year. The contract listing page is where every mobile buyer on that program lands first — it's the entry point to the platform, not a secondary screen.

That page was built roughly seven years ago, on AngularJS (now unsupported and a standing security concern) with Bootstrap 3.4.1 components. It was never built to handle the dataset it was now serving: 150+ columns, with no clean existing way to represent that much structure on a single grid.

Problem

A 20-second load that blocked everything else

Load times on the listing page ran as high as 20 seconds. Until the page finished loading, every other action on it was blocked — there was no partial interactivity to fall back on. That's a structural constraint I couldn't route around; it had to be fixed at the source.

15–20 second load → page usable
Diagnosis

I went to engineering before I went to a redesign brief

Before scoping anything, I worked with engineering to confirm the actual root cause rather than assume it was a frontend problem. Live data for every contract required joins across separate tables, for every one of 150+ columns, on every page load. The data model itself — not the UI — was the bottleneck.

Two other things pushed this from "optimize the existing page" to "rebuild it":

  • A feature request that couldn't be bolted on. The client had paid for two new capabilities — advanced condition-based search and saved/preset views — and adding either to the legacy page wasn't viable without the rebuild anyway.
  • A dead stack. AngularJS and Bootstrap 3.4.1 weren't just old; building new capability on top of them didn't make technical sense. That reinforced the case for a ground-up rebuild over an incremental patch.
Approach

Flatten the data, sync it in real time, load it lazily

I scoped and specced the rebuild around three technical decisions, arrived at after evaluating multiple approaches with engineering:

  • Flattened the data model — removing the per-load joins that were the actual bottleneck
  • OpenSearch + Kafka for real-time sync, replacing the old approach of computing everything live on request
  • Server-side lazy loading in place of client-side pagination, so the browser was never asked to hold the full dataset at once

The hardest problem showed up after the first OpenSearch pass: data was still frequently stale, because nothing was feeding OpenSearch the latest state on every relevant change. I personally mapped every user action across the platform that could update any of the 150 data points, and built the pipelines to make sure OpenSearch reflected current state — not the state it had when it was last indexed.

Execution

A hard cutover, with a rollback plan on standby

This ran end to end in about 2.5 months with three senior engineers (full-stack, backend, frontend) and me as PM — while I was also managing other products concurrently, since I'm the only PM across two of ScopeWorker's three squads.

I owned the rollout risk directly:

  • Migrated existing users' saved dashboard state into the new version, so nobody lost their default view
  • Anticipated that users would need to relearn where bulk actions moved to in the new UI
  • Planned a hard cutover overnight — no dual-support period for old vs. new — with a rollback plan prepared in case of major pushback

The rebuild also shipped real bulk actions that didn't exist before: updating contract start/end dates across multiple contracts at once, assigning contracts to multiple suppliers, canceling multiple contracts, bulk-assigning agents, bulk-downloading PO/contract documents, plotting multiple contracts on a map, and viewing line items across all contracts at once.

Results

3–4.5 second loads, and a full adoption signal on top

The 93% figure comes from ScopeWorker's per-feature success rating, where users score a launched feature 1–5 after using it — averaged out to a percentage across the new dashboard, table structure, advanced search, and saved views together, not any single sub-feature in isolation.

What I'd do next

Default to active contracts, not full history

The page currently still loads and scrolls through the full contract history by default — including dormant contracts three-plus years old. I'd propose defaulting to active-only contracts instead, which would cut computation cost further on top of the load-time win already shipped. I haven't pitched this to the client yet, but it's the next lever I'd pull.
